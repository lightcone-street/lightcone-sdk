# Spice, Sury, and Serde

Research date: 2026-10-13. This is a dependency comparison, not an approved migration or SDK contract change.

Keep Spice for the browser SDK under the current deployment policy. Sury has useful validation and schema capabilities, but its published 11.0.0 documentation explicitly states that it has no mode without dynamic code evaluation. The parent application's [CSP](../../../../src/service/web_security.rs#L157) permits WebAssembly evaluation without permitting JavaScript `unsafe-eval`; its [test](../../../../src/service/web_security.rs#L2277) enforces that distinction. Sury's optional PPX generates schemas and does not remove this runtime dependency. [Sury runtime requirements](https://github.com/DZakh/sury/blob/v11.0.0/packages/sury/README.md#is-new-function-safe-to-use).

Spice's strength is a small, type-driven JSON interface: annotate a ReScript declaration and receive encoder and decoder functions. Custom codecs cover unusual boundaries, and decoder failures carry a path, message, and input value. Its narrower purpose keeps ordinary DTOs straightforward. Its costs are compiler/PPX compatibility and manual work for richer validation or schema introspection. Variant payload encodings and missing-versus-null semantics require deliberate adaptation to backend contracts. [Spice guide](https://github.com/mununki/ppx_spice/blob/main/docs/GUIDE.md).

Sury's strength is reusable schemas: validation constraints, transformations, explicit null handling, JSON Schema generation, and Standard Schema integration. It supports both ReScript and TypeScript. ReScript users can write schemas directly or derive them with `sury-ppx` and `@schema`, so migrating does not inherently require duplicating every record definition. Constraints and custom schemas can remain attached to types. [Sury PPX](https://github.com/DZakh/sury/blob/v11.0.0/packages/sury-ppx/README.md), [ReScript API](https://github.com/DZakh/sury/blob/v11.0.0/docs/rescript-usage.md).

The corresponding costs are a larger API to learn, a runtime schema compiler, initialization and bundle overhead to measure, and the deployment restriction above. Its compiled operations are designed for high throughput, but published benchmarks do not establish a speed advantage over this SDK's Spice codecs or Rust Serde. Measure representative success and failure payloads, startup, and shipped bundle size before making performance claims.

Serde shares Spice's type-first derivation style, while supporting many formats through separate serializer/deserializer implementations such as `serde_json`. Rust traits and compile-time generation avoid runtime reflection. Borrowed deserialization can avoid copying eligible input data. Arbitrary domain validation still needs custom deserialization or separate validation; JSON Schema generation comes from companion crates such as Schemars. Its tradeoffs include derive/build complexity and more involved custom implementations. It remains the natural Rust counterpart rather than a JavaScript replacement. [Serde design](https://serde.rs/), [custom deserialization](https://serde.rs/impl-deserialize.html), [borrowing](https://serde.rs/lifetimes.html), [Schemars](https://docs.rs/schemars/latest/schemars/).

Two local compatibility boundaries deserve particular attention in any later experiment. [ExactJson](../src/ExactJson.res) preserves large JSON integer tokens and emits unquoted integers; Sury's standard JSON bigint example uses strings. Replacing the lossless parser with ordinary JSON parsing could lose precision before schema validation begins. [SdkError.stripNulls](../src/SdkError.res#L307) compensates for Spice optional-field decoding; Sury's nullable options could express this locally, but missing, null, and encoded output behavior must stay compatible.

Consider Sury first for server-side validation or schema reuse where dynamic evaluation is allowed. Revisit browser replacement if a supported CSP-compatible execution mode becomes available. Preserve exact integer and decimal boundaries, enum representations, null behavior, and error contracts in any parity assessment.
